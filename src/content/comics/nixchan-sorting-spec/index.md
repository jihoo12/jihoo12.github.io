증명이 확인하는 것은 **우리가 적은 명제**예요. 모든 입력에 `[]`를 반환하는 함수도 출력이 정렬돼 있다는 조건은 만족해요. 빈 리스트에는 순서를 어기는 원소 쌍이 없으니까요.

정렬 함수의 명세에는 **출력이 정렬돼 있다**와 **출력이 입력의 순열이다**가 함께 필요해요. 순열 보존은 원소의 값뿐 아니라 중복 개수까지 보존한다는 뜻이에요. 예를 들어 `[3, 1, 1]`은 `[1, 1, 3]`으로 정렬해야 하며, `[]`나 `[1, 3]`으로 바꾸면 안 돼요. 길이만 같거나 원소의 집합만 같다는 조건으로도 충분하지 않아요.

만화 속 `Sorted (sort xs)`는 특정 라이브러리의 실행 가능한 Lean 코드가 아니라 명세를 요약한 표기예요. Lean이 잘못된 증명을 받아들인 이야기가 아니라, 사람이 너무 약한 명제를 골랐다는 이야기예요. 명세를 강화한 뒤에는 구현도 그 명세를 만족하도록 고치고 두 조건을 모두 증명해야 해요.

## 대사와 화면 내용

1. **증명 완료.** 닉스쨩: “정렬됨, 증명 완료!” 노트북: `Sorted (sort xs)`와 초록색 확인 표시.
2. **사라진 원소.** 닉스쨩: “잠깐, 원소는 어디 갔어?!” 화면: `sort [3, 1, 2] = []`.
3. **빠진 조건 발견.** 닉스쨩: “빈 리스트도 정렬돼 있네...” 체크리스트: “정렬됨 ✓”, “입력 원소 보존 ?”. 강조 문구: “명세에 빠진 조건!”
4. **명세 수정.** 닉스쨩: “오늘 고칠 건 명세였네!” 새 체크리스트: “정렬됨 + 순열 보존”. 옆에는 1, 2, 3 숫자 블록이 모두 남아 있다. 하단 크레딧: “dot / Codex”.
